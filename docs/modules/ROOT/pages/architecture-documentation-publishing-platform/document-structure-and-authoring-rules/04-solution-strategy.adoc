== 4.1 文書をコードの近くに置く

各ソースリポジトリは、そのリポジトリが責任を持つシステム、
サブシステム、ライブラリ、設定、運用の文書正本を保持する。

これにより、コードと文書を同じ変更単位で扱い、
リポジトリ内のAIやレビュー担当者が両方を参照できるようにする。

== 4.2 全体と部分を階層化する

親文書は全体の目的、境界、部分間の関係を説明する。
詳細が独立した責務、構成、実行時動作、品質、リスクを持つ場合は子arc42へ分ける。

親には要約と子文書への``xref``を残し、
詳細は子文書だけを正本とする。
子文書は親へ戻るリンクと、直接関係する他の子文書へのリンクを持つ。

== 4.3 安定した識別子を使う

文書directoryは対象を表す英小文字kebab-caseのslugとする。
表示順やarc42章番号はdirectory名へ含めず、章番号は章ファイル名に持たせる。

ページ参照はfilesystem上の相対位置ではなく、
Antora moduleの``pages/`` rootを基準にしたresource IDを標準とする。

== 4.4 再利用と説明を分ける

独立して読ませる内容はpage、複数ページへ埋め込む断片はpartialに置く。
同じ説明を複数ページへコピーせず、読者を別文書へ移動させる場合は``xref``、
同一内容をページの一部として再利用する場合は``include``を使う。

== 4.5 確認可能な執筆

文書は小さな変更単位で作成し、メタデータ、navigation、xref、
関連する図と検査を同時に更新する。
pull request前にローカル内容を読むAntora buildを実行し、
生成HTMLの見出し、表、コードブロック、リンク、図を確認する。
