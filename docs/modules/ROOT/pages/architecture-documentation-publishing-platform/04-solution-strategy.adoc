== 4.1 基本方針

アーキテクチャ文書公開基盤は、文書本文の正本を各ソースリポジトリに残し、公開表示だけを専用サイトリポジトリで集約する構成にする。

この基盤の解決方針は、以下の組み合わせで成立させる。

* 文書体系はarc42を基本にする。
* 文書形式はAsciiDocにする。
* 文書配置はAntora標準構成に寄せる。
* 図の正本はStructurizr DSLにする。
* 公開サイト生成は専用サイトリポジトリのAntora playbookで行う。
* 公開先はGitHub Pagesにする。
* 更新契機は各ソースリポジトリの`main`更新とする。
* 自動再生成は`repository_dispatch`、手動再生成は`workflow_dispatch`で扱う。

この章では、詳細な実装手順ではなく、後続章の前提になる主要な解決戦略だけを示す。

== 4.2 文書正本を各ソースリポジトリに置く戦略

各ソースリポジトリは、そのリポジトリが責任を持つシステム、サブシステム、ライブラリ、設定、運用などのアーキテクチャ文書を正本として保持する。

文書正本をソースリポジトリに置く理由は、以下である。

* コード変更と文書変更を同じ変更単位で扱える。
* Codexなどのリポジトリ内AIが、コードと文書を同時に参照・編集しやすい。
* 文書だけが別の場所で古くなる状態を避けやすい。
* サブシステム単位のarc42文書を、そのサブシステムの近くに置ける。

GitHub Pages上の公開サイトは、閲覧用の派生成果物であり、文書正本ではない。

== 4.3 専用サイトリポジトリで集約・公開する戦略

複数のソースリポジトリにある文書は、専用サイトリポジトリで集約する。

専用サイトリポジトリは、以下を持つ。

* Antora playbook
* 公開workflow
* 共通UI
* 共通検査ツール
* 必要な公開設定

各ソースリポジトリは、原則として自分の文書正本と最低限の検査・生成設定を持つ。統合サイト全体の構成、複数リポジトリの取り込み順、GitHub Pagesへのdeployは専用サイトリポジトリ側の責務にする。

この分離により、ソースリポジトリ側は「文書を書く場所」、サイト用リポジトリ側は「集めて公開する場所」として扱える。

== 4.4 AsciiDoc / Antora / arc42 を使う戦略

文書本文はAsciiDocで書き、arc42の章構成に沿って分割する。

AsciiDocを使う主な理由は、以下である。

* arc42公式テンプレートとの相性がよい。
* `include`や属性などにより、章・節単位の再利用がしやすい。
* Antoraの文書体系に自然に乗せられる。
* 図、コードブロック、表、相互参照を文書化基盤として扱いやすい。

Antoraを使う主な理由は、以下である。

* 複数リポジトリの文書をcontent sourcesとして集約できる。
* component、module、page、partial、assetという構造で文書群を管理できる。
* GitHub Pagesに出す静的サイトを生成できる。
* `xref`により、相対パスより安定したページ間参照を使える。

arc42は、システムごとのアーキテクチャ説明の型として使う。単一の巨大なarc42ですべてを表すのではなく、全体文書とサブシステム文書を階層的に組み合わせる。

== 4.5 Structurizr DSLを図の正本にする戦略

アーキテクチャ図の正本はStructurizr DSLにする。

arc42本文には、Structurizr DSLそのものを主たる図表現として直接埋め込まず、DSLから生成したSVGなどの画像を埋め込む。

この方針により、以下を分離する。

[cols="1,3",options="header"]
|===
| 対象
| 役割

| Structurizr DSL
| 図モデルの正本。変更はまずDSLに入れる。

| 生成済みSVG / PNG
| 公開サイトで閲覧するための派生成果物。

| arc42本文
| 図を説明し、生成済み画像を参照する文書。
|===

Structurizr DSLからSVGを直接生成するか、PlantUML / C4-PlantUML経由にするかは未決定であり、11章の技術的リスクとして扱う。

== 4.6 英語正本・日本語補助版の運用戦略

造智機巧本体のアーキテクチャ文書は、英語版を正本、日本語版を補助版として扱う。

ただし、この`meta_architecture`自体は日本語運用の文書であるため、英語正本・日本語補助版の必須対応検査の対象外にする。

日英版を持つ文書では、同一component内のAntora moduleで言語を分ける。

[cols="1,2",options="header"]
|===
| module
| 役割

| `ROOT`
| 英語正本

| `ja`
| 日本語補助版
|===

草稿段階では片方だけの更新を許容する。公開時と版確定時には、対応ページの欠落と`:lang:`不一致をCIで検出する。

== 4.7 自動化と手動再実行の戦略

文書作成者は、原則として文書本文、図定義、必要な参照を書き、`main`ブランチへ反映するところまでを行う。

その後の文書検査、図生成、サイト生成、GitHub Pages公開は、GitHub Actionsで自動化する。

自動化の起動方式は以下とする。

[cols="1,2,3",options="header"]
|===
| 起動方式
| 起動元
| 用途

| `repository_dispatch`
| ソースリポジトリの`main`更新後
| サイト用リポジトリの公開workflowを自動起動する。

| `workflow_dispatch`
| Fまたは保守者の手動操作
| 失敗後の再実行、設定変更後の再生成、確認用の手動公開に使う。
|===

`repository_dispatch`だけにすると手動再実行が面倒になるため、サイト用リポジトリの公開workflowは`workflow_dispatch`も受け付ける。

== 4.8 現時点で保留する判断

以下は、現時点では戦略として固定せず、未決定事項または技術的リスクとして管理する。

* Structurizr DSLの分割単位と`!include`配置規則
* Structurizr DSLからSVGを直接生成するか、PlantUML / C4-PlantUML経由にするか
* private repositoryの文書をpublic GitHub Pagesへ出してよいか
* docToolchainのAntora連携をどこまで使うか
* `zouchikikou-docs-site`の初期作成手順と最小構成
* cross-repository workflowで使うtoken / secret管理
* サイト再生成失敗時の通知・再実行手順
* Antora UI上の日英切り替え導線
* サイト用リポジトリ作成後の`tools/check-language-pairs`実装
* 日英対応ページの内容差分や更新鮮度の検査要否
