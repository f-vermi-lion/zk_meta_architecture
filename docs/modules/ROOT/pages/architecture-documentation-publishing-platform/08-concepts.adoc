== 8.1 正本と派生成果物

この基盤では、正本と派生成果物を明確に分ける。

[cols="1,2,1,3",options="header"]
|===
| 成果物
| 所在
| 正本か
| 説明

| arc42章・節AsciiDoc
| 各ソースリポジトリ
| はい
| 文書本文の正本。章または節単位で分割する。

| Structurizr DSL
| 各ソースリポジトリ
| はい
| C4図モデルの正本。図の変更はまずDSLへ入れる。

| Structurizr JSON workspace
| 各ソースリポジトリ
| いいえ
| 手動レイアウトを含むexport入力。モデル正本ではなく、SVG生成時の見た目再現に使う。

| Antora component descriptor
| 各コンテンツルート
| はい
| Antora component versionの識別・設定。

| navigation file
| 各component/module
| はい
| サイト内ナビゲーションの正本。

| Antora playbook
| サイト用リポジトリ
| はい
| どのリポジトリ・ブランチ・パスから文書を集めるかを定義する。

| GitHub Actions workflow
| 各ソースリポジトリまたはサイト用リポジトリ
| はい
| 検査、生成、デプロイの自動化定義。

| GitHub Pages公開サイト
| GitHub Pages
| いいえ
| 利用者向けの公開結果。正本ではない。

| 生成済みSVG
| build出力またはassets
| いいえ
| Structurizr DSL/JSONから直接生成される派生成果物。
|===

GitHub Pages上の公開結果や生成済み画像を直接編集して正本化しない。

== 8.2 Antora標準構成

文書は、Antora標準構成に沿って配置する。

[source,text]
----
docs/
  antora.yml
  modules/
    ROOT/
      nav.adoc
      pages/
      partials/
      assets/
    ja/
      nav.adoc
      pages/
      partials/
      assets/
----

`ROOT` moduleは、英語正本を置く標準moduleとして使う。日本語補助版を持つ場合は、`ja` moduleを使う。

`meta_architecture`自体は日本語運用のため、現時点では`ROOT` moduleに日本語ページを置いている。

最初の実装候補は以下である。

[source,text]
----
source-repo-a/
  docs/
    antora.yml
    modules/
      ROOT/
        nav.adoc
        pages/
          index.adoc
          01-introduction-and-goals.adoc
          02-architecture-constraints.adoc
          03-context-and-scope.adoc
        partials/
        examples/
          diagrams/
            structurizr/
              workspace.dsl
              workspace.json
        assets/
          images/
            diagrams/
              system-context-docs-site.svg
      ja/
        nav.adoc
        pages/
          index.adoc
          01-introduction-and-goals.adoc
          02-architecture-constraints.adoc
          03-context-and-scope.adoc
  docToolchainConfig.groovy
  dtcw

zouchikikou-docs-site/
  README.md
  antora-playbook.yml
  package.json
  .gitignore
  .github/
    workflows/
      build.yml
  tools/
    README.md
----

この構成なら、arc42文書の正本を各ソースリポジトリに置きつつ、Antoraの複数リポジトリ集約とGitHub Pages公開に自然につなげられる。

== 8.3 arc42章ファイル構成

arc42本文は、章ごとのファイルに分ける。

ファイル名は、`NN-chapter-slug.adoc`形式にする。

`NN`はarc42の章番号を2桁ゼロ埋めで表す。

標準slugは以下である。

[cols="1,2",options="header"]
|===
| 章番号
| ファイル名

| 1
| `01-introduction-and-goals.adoc`

| 2
| `02-architecture-constraints.adoc`

| 3
| `03-context-and-scope.adoc`

| 4
| `04-solution-strategy.adoc`

| 5
| `05-building-block-view.adoc`

| 6
| `06-runtime-view.adoc`

| 7
| `07-deployment-view.adoc`

| 8
| `08-concepts.adoc`

| 9
| `09-architecture-decisions.adoc`

| 10
| `10-quality-requirements.adoc`

| 11
| `11-technical-risks.adoc`

| 12
| `12-glossary.adoc`
|===

必要な章だけを置いてよい。まだ判断材料が足りない章は、空の章ファイルを増やすより、未決定事項や技術的リスクとして管理する。

== 8.4 日英運用

造智機巧本体のアーキテクチャ文書は、英語正本と日本語補助版で運用する。

[cols="1,2,2",options="header"]
|===
| 言語
| Antora module
| 扱い

| 英語
| `ROOT`
| 正本

| 日本語
| `ja`
| 補助版
|===

日英で対応するページは、module配下の相対パスとファイル名を揃える。

草稿段階では片方だけの更新を許容する。公開時と版確定時には、対応ページの欠落と`:lang:`不一致をCIで検出する。

== 8.5 図定義と生成画像

図ソースは、対応するAntora module配下の`examples/diagrams/`に置く。公開画像は、対応するAntora module配下の`assets/images/diagrams/`に置く。

標準配置は以下である。

[source,text]
----
docs/modules/<module>/examples/diagrams/                     # diagram source root
docs/modules/<module>/examples/diagrams/structurizr/workspace.dsl   # C4 model source
docs/modules/<module>/examples/diagrams/structurizr/workspace.json  # C4 layout workspace
docs/modules/<module>/examples/diagrams/structurizr/model.dsl       # optional model split
docs/modules/<module>/examples/diagrams/structurizr/views.dsl       # optional view split
docs/modules/<module>/examples/diagrams/structurizr/styles.dsl      # optional style split
docs/modules/<module>/assets/images/diagrams/                # generated diagrams
----

C4/Structurizrでは、1つのAntora moduleにつき1つのStructurizr workspaceを置く。標準入口は常に`workspace.dsl`にする。

小規模なうちはDSLを分割しない。分割が必要になった場合は、`examples/diagrams/structurizr/`直下に`model.dsl`、`views.dsl`、`styles.dsl`を置き、`workspace.dsl`から相対パスで`!include`する。さらに大きい場合だけ、`examples/diagrams/structurizr/model/`や`examples/diagrams/structurizr/views/`配下へ細分化する。

`!include`は`examples/diagrams/structurizr/`配下のDSLソースツリー内に限定する。`pages/`、`partials/`、`assets/images/`、別module、リポジトリ外ファイルは参照しない。

C4図の標準生成経路は、Structurizr DSL/JSONからStructurizrの`export -format svg`で直接SVGを生成する方式にする。

Structurizr図生成CI workflowは、図を持つ各ソースリポジトリの`.github/workflows/diagrams.yml`に置く。起動条件は、`pull_request`、`main`への`push`、手動の`workflow_dispatch`とする。初期標準では`paths` filterを使わず、workflow内のworkspace自動検出で図生成対象なしを成功扱いにする。

標準Docker imageは`structurizr/structurizr:2026.05.22-playwright`とする。Docker image tagは日付付き`-playwright` tagを固定し、`latest`や未修飾tagは使わない。tag更新は月次確認または必要時の専用変更として手動で行う。標準コマンドは以下である。

[source,sh]
----
docker run --rm -v "$PWD:/usr/local/structurizr" structurizr/structurizr:2026.05.22-playwright export -format svg -workspace docs/modules/<module>/examples/diagrams/structurizr/workspace.json -output docs/modules/<module>/assets/images/diagrams
----

生成対象は以下で自動検出する。対象が0件の場合は、図生成対象なしとして成功扱いにする。

[source,sh]
----
find docs/modules -path '*/examples/diagrams/structurizr/workspace.json' -type f -print
----

生成SVGは派生成果物だが、Antora assetとしてリポジトリ管理する。Antoraページからは`image::diagrams/<file>.svg[]`で参照する。

再生成後の未反映差分は以下で検出する。

[source,sh]
----
git status --porcelain -- docs/modules/<module>/assets/images/diagrams
----

出力が空なら成功、空でなければ未反映差分ありとしてCIを失敗させる。失敗時は以下をlogに出す。

[source,sh]
----
git status --short -- docs/modules/<module>/assets/images/diagrams
git diff -- docs/modules/<module>/assets/images/diagrams
----

`workspace.json`は、手動レイアウトを再現するためのレイアウト付きexport入力として管理する。モデル変更の出発点は引き続き`workspace.dsl`にする。

モデル変更時は`workspace.dsl`を更新し、既存`workspace.json`のレイアウトを反映した状態で`workspace.json`を更新する。レイアウトだけを調整する場合は、`workspace.json`の変更だけを許容する。

`workspace.json`は手編集せず、StructurizrのUIまたは公式ツールのmerge/export結果として更新する。

レイアウト保持のため、Structurizr viewsには明示的で安定したview keyを付ける。形式は`<view-type>-<target>[-<purpose>]`の英小文字kebab-caseにする。

`view-type`の標準語彙は、`system-context`、`container`、`component`、`dynamic`、`deployment`、`filtered`、`image`、`custom`である。`target`と`purpose`は安定したslugにし、arc42章番号や一時的な表示名は含めない。

例:

[source,text]
----
system-context-docs-site
container-docs-site
dynamic-publish-flow
deployment-docs-site-production
----

arc42本文では、生成済み画像をAsciiDocの`image::diagrams/<file>.svg[]`で参照する。

DSL断片をarc42本文へ主たる図表現として直接埋め込まない。

== 8.6 相互参照とinclude

Antora上のページ間参照は、`xref`を基本にする。

[source,asciidoc]
----
xref:architecture-documentation-publishing-platform/03-context-and-scope.adoc[3. コンテキストとスコープ]
----

再利用する断片は、対応するmoduleの`partials/`配下に置き、AsciiDoc includeで取り込む。

[source,asciidoc]
----
\include::partial$example.adoc[]
----

リポジトリ内外のページ参照では、相対パスよりAntoraのresource IDを優先する。

== 8.7 文書メタデータ

各arc42ページには、以下のメタデータを置く。

[source,asciidoc]
----
= 文書タイトル
:docstatus: draft
:created: YYYY-MM-DD
:revdate: YYYY-MM-DD
:authors: F; ChatGPT
:lang: ja
----

`:docstatus:`は、`draft`、`reviewed`、`published`のいずれかにする。

`:created:`と`:revdate:`は、`YYYY-MM-DD`形式にする。

`:lang:`は、`en`または`ja`にする。

== 8.8 CI検査

CI検査は、文書内容以外の機械的な問題を早期に検出するために使う。

検査対象は以下である。

* AsciiDoc構文
* 必須メタデータ
* `xref`とinclude
* Structurizr DSL構文
* 生成済み図の存在
* 日英対応ページの欠落
* `:lang:`不一致
* Antora build

検査のうち、複数リポジトリ横断でないものはソースリポジトリ側で行ってよい。複数リポジトリ横断の検査と最終的なAntora buildは、サイト用リポジトリ側で行う。
