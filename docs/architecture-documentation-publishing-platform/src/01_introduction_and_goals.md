## 1. 導入と目的

### 1.1 要件の概要
各ソースリポジトリでarc42アーキテクチャ文書とstructurizrDSLなどを更新したら
GitHubサイトが更新される
Doctoolchain,Antora,structurizrを使う

### 1.2 品質目標


| 品質目標              | 動機と説明                                                           |
| ----------------- | --------------------------------------------------------------- |
| 文書内容以外の自動化        | 文書と図を書いてそれぞれのオリジンのmainにプッシュされたら、<br>後は自動でGitHub Pagesのサイトに反映される |
| 文書とソースのリポジトリを同一に  | ソースのリポジトリにそこが正本となるべき文書を配置、管理できる。                                |
| 章または節ごとの文書ファイル    | LLMの効率と、他文書との共有のため。<br>章ごと、それでも長いなら節ごとにファイルを分けて全体用のファイルに取り込む。   |
| 関連する別リポジトリの文書取り込み | 横断的概念や全体と部分の関係の関連リポジトリの文書を取り込む。                                 |
| 草稿段階で試し読み可能       | 取り込みが狂っていないかや図の表示などはすぐに試し読みで確認したい                               |
| 日英対応              | Fは日本語のみ、Codexは英語の方が得意、両方連携対応できるようにする                            |
| 既存の道具や型に乗る        | 目的に合うものがあるなら自分だけで作ろうとするのでなく使えるものを使うと効率的                         |


### 1.3 ステークホルダー

| 役割/名前    | 期待                                                                               |
| -------- | -------------------------------------------------------------------------------- |
| F        | 文書に関しては基本的に内容にだけ注意を払ってそれ以外は自動化したい<br>サイトでは日本語で読みたい                               |
| Codex    | ソースのリポジトリに文書もあった方がやりやすい。<br>意味のあるまとまりである程度の大きさのファイルに分かれていると効率が良い<br>英語の方が性能が良さそう |
| ChatGPT  | 意味のあるまとまりである程度の大きさのファイルに分かれていると効率が良い                                             |
| リポジトリ貢献者 | 以上の3者に準ずる                                                                        |
| 文書サイト閲覧者 | 特定文書なら鏈接を開くだけで読める<br>サイトの使い方が分かりやすい<br>詳細と概要、隣接情報を辿りやすい                          |
