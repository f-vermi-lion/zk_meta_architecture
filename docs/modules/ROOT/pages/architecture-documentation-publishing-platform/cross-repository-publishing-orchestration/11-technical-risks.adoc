== 11.1 token / secret管理

cross-repository dispatchには、別repositoryを操作できる認証が必要になる。
権限が広すぎる、secretが増える、漏洩時に他repositoryへ影響するリスクがある。

tokenの種類、権限、保存場所、rotationは未決定である。
決定するまでは自動dispatchを有効化せず、
手動site workflowを復旧経路として維持する。

== 11.2 失敗通知

workflowが失敗しても保守者が気づかなければ、
公開siteが古いまま残る。

通知方法、通知先、確認担当、再実行手順は未決定である。
少なくとも失敗した処理、content root、file、commandをlogへ残し、
``workflow_dispatch``から再実行できるようにする。

== 11.3 event契約

``repository_dispatch``のevent type、payload、送信元の識別、
重複eventや短時間の連続更新の扱いが未確定である。

site buildはpayload内の文書を正本にせず、
playbookからcontent sourcesを取得する。
event契約を決めるときは、複数sourceの同時更新とconcurrencyも確認する。

== 11.4 checkerへ渡すcontent root

Antoraはcontent sourcesを内部で取得するが、
site workflowが日英checkerへ渡せるcheckout済みcontent rootを
どの手順で用意・列挙するかは未決定である。

取得方法が決まるまでは、checker実装済みとpublish gate統合済みを区別する。
一時directory、cache、private repository認証を含めて設計する必要がある。

== 11.5 reusable workflowの参照

図生成callerは初期例でreusable workflowを``@main``参照する。
upstream変更が複数sourceへ同時に影響する可能性がある。

tagまたはreleaseへ固定する運用方針は未決定であり、``inbox.md``で扱う。
固定方法を決めるまでは、共通workflow変更時にcallerと生成結果への影響を確認する。

== 11.6 private content source

private repositoryの取得権限とpublic Pagesへの公開可否が未決定である。
dispatch権限だけでなく、site buildがcontentを読む権限、
artifactとlogへ出る情報も公開境界に含める必要がある。

初期標準はpublic content sourceに限定する。
